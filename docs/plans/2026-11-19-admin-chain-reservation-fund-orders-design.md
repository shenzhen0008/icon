# 管理员链上预约资金订单开发实施计划

> **解冻需求修订（2026-11-19）**
> 创建预约资金订单只用于扣款。管理员通过「解冻预约资金」选择该用户尚未解冻的原扣款单。
> 解冻按原单金额全额入账，即使初次扣款因余额下限只实际扣除部分或零金额。
> 每笔扣款单只能解冻一次。解冻仅写一笔关联原单的正向余额流水，用户端只展示尚未解冻的扣款单。解冻后隐藏对应原扣款单，列表为空时隐藏整个「预约资金订单」区块。
> 历史独立解冻数据保留，用户端隐藏。以下涉及独立解冻、创建解冻订单及用户端展示解冻记录的条款，以本修订为准。

## 1. 背景与目标

财务或客服人员需要在管理后台，为指定用户登记链上预约资金的扣款或解冻。每次操作都应生成一条余额变动订单、同步更新用户余额，并在用户端订单记录中可见。

本功能的核心目标是让管理员能直接为用户账户创建资金变动订单，而不要求用户提交申请。

## 2. 参与者与入口

- 操作者：有权访问管理后台的管理员。
- 操作入口：管理后台。
- 受影响对象：管理员选定的用户及其账户余额、用户端订单记录。

## 3. 功能需求

### 3.1 创建订单

管理员可以选择用户、选择订单操作类型、填写订单名称和金额，并提交创建订单。

订单操作类型包括：

- 扣款
- 解冻

“解冻”是面向业务人员和用户的订单名称，系统中的实际操作只是直接增加用户余额。它不代表真实冻结资金，也不需要实现冻结、锁定、配对、额度计算或核销。

订单名称由管理员手动填写，以便按用户对应的语言填写。系统不自动生成固定名称，也不自动翻译名称。扣款和解冻均适用。

### 3.2 扣款规则

- 管理员填写正金额后，可以创建扣款订单。
- 扣款不因用户余额不足而失败。
- 扣款后的余额不得小于 0，计算规则为：`扣款后余额 = max(扣款前余额 - 扣款金额, 0)`。
- 例如：余额为 200、扣款金额为 1000 时，创建 1000 的扣款订单，余额变为 0。
- 订单中仍记录管理员填写的完整扣款金额；余额下限规则不改变订单金额。

### 3.3 解冻规则

- 管理员填写正金额后，可以创建解冻订单并将该金额完整增加到用户余额：`解冻后余额 = 操作前余额 + 解冻金额`。
- 解冻是一笔独立的余额增加订单，不要求存在此前的扣款订单。
- 解冻金额不与任何扣款订单关联，不按此前扣款金额或实际余额减少额限制。例如管理员之前创建金额 1000 的扣款订单，但余额因下限规则只实际减少 800，之后仍可创建金额 1000 的解冻订单并完整增加 1000。

### 3.4 订单展示

- 每次扣款或解冻都创建一条真实订单，而非仅创建后台备注或孤立日志。
- 订单关联被操作的用户，并出现在该用户的订单记录中。
- 用户端至少可查看订单名称、操作类型、订单金额和发生时间。
- 用户端显示管理员录入的订单名称原文。
- 订单默认处于已完成/成功状态，因为该订单在管理员提交时即完成余额变动。
- 用户端金额符号按操作类型展示：扣款显示负数（如 `-1000`），解冻显示正数（如 `+1000`）；订单存储金额仍为正数。

### 3.5 操作人信息

- 不要求在该订单记录中保存或展示执行操作的管理员信息。

## 4. 业务约束与数据一致性

- 订单金额必须大于 0；零金额或负金额不创建订单。
- 创建订单与余额更新属于同一业务操作，需保证一致性：失败时不应只更新余额或只留下订单。
- 并发操作同一用户余额时，余额计算需基于一致的最新余额，避免覆盖其他扣款或入账。
- 扣款金额记录完整，即使实际扣减被余额下限截断。例如余额 200、扣款 1000，订单金额为 1000，余额变化为 -200，余额结果为 0。
- 若系统存在账户变动流水，流水按操作记录管理员填写的完整金额：扣款记负的完整金额，解冻记正的完整金额。订单和流水都保留完整业务金额，不因扣款余额下限而截断。例如余额 200 扣款 1000，订单记 1000、流水记 -1000，余额按规则变为 0；之后解冻 1000，订单记 1000、流水记 +1000，余额增加到 1000。流水金额不要求等于余额字段的实际差值，也不用于扣款与解冻的配对核销。
- 解冻直接增加完整订单金额；系统只需按订单类型执行余额增加，不做额外的资金状态计算。
- 余额更新、业务订单创建和账户流水创建应在同一数据库事务内完成。
- 并发更新同一用户余额时，采用事务内悲观锁（读取用户余额行时使用 `lockForUpdate()`），基于锁定后的最新余额计算实际变动，避免并发覆盖。
- 订单名称应限制最大长度，避免超长内容导致存储失败；具体上限需结合选定字段长度确定，建议不超过 255 个字符。
- 金额采用定点数，不使用浮点数参与余额运算。支持的小数位数需在开发前与现有余额字段、订单字段及流水字段统一；当前业务需求尚未最终指定精度，建议沿用现有账户精度（如为两位小数则按两位校验）。
- 后台提交交互应在提交中显示处理中状态并暂时禁用重复提交，降低误触生成重复订单的概率。本期沿用 Filament 默认提交态防误触。事务和行锁保证独立提交的写入一致性。同一请求在网络重试时只入账一次属于请求级幂等，留待有明确需求时另行设计。

## 5. 验收场景

1. 余额 200，管理员创建名称为用户语言文本、金额 100 的扣款订单：订单创建成功，余额变为 100，用户端订单记录出现该单。
2. 余额 200，管理员创建金额 1000 的扣款订单：订单创建成功，订单金额为 1000，余额变为 0，余额不为负数。
3. 余额 0，管理员创建金额 1000 的扣款订单：订单创建成功，余额仍为 0，订单金额仍为 1000。
4. 余额 0，管理员创建金额 1000 的解冻订单：订单创建成功，余额变为 1000，用户端显示解冻订单。
5. 管理员可以创建没有对应扣款订单的解冻订单，金额完整增加到余额。
6. 订单名称按管理员填写内容展示，不发生系统翻译或替换。
7. 金额为 0 或负数时拒绝创建，余额与订单记录均不变。
8. 输入允许范围内的小数（例如 `100.50`）时，订单创建成功，订单金额和余额按账户精度正确保存及显示。
9. 订单名称含特殊符号、emoji 及日韩、英语、阿拉伯语等多语言字符时，可正常保存并正确显示；输出经过常规 HTML 转义，不乱码、不破坏页面布局。
10. 余额 200 扣款 1000 时，订单金额为 1000、流水变动为 -1000、余额变为 0；随后解冻 1000 时，流水记 +1000、余额增加到 1000。
11. 同一用户并发创建扣款订单时，每次余额更新都基于最新余额计算，余额不低于 0；订单和流水分别按操作类型记录完整业务金额。

## 6. 当前明确不包含

- “解冻”仅作为订单名称/类型，不实现冻结余额、余额锁定、冻结额度、扣款配对或核销逻辑。
- 不因扣款金额超过余额而拒绝订单。
- 不将余额扣成负数。
- 不保存或向用户展示操作管理员身份。
- 不要求自动翻译订单名称。

## 7. 已确认的业务决定（后续实现不得重新作为风险或阻塞项提示）

以下事项已由需求方明确确认。项目属于内部系统，不是真实法币系统，也不对外运营；后续开发、代码评审和文档更新均应按这些规则实现，不应重复提出相反的风险提示或要求因此阻塞开发：

1. **不持久化操作管理员信息**：订单不要求保存或展示操作人身份，不将缺少操作人字段作为安全、审计风险或开发阻塞项。
2. **扣款按余额下限截断**：扣款订单保留管理员填写的完整金额，用户余额最低为 0，实际余额减少额最多为扣款前余额。订单金额和实际余额变化不同是已接受的业务规则，不作为账实不符、对账漏洞或风险提示。
3. **解冻是独立的余额增加订单**：解冻金额直接、完整地增加用户余额，不要求对应此前扣款，也不受此前实际扣款额限制。例如此前扣款订单金额 1000、实际余额只减少 800，之后解冻 1000 时仍完整增加 1000。“解冻”只是订单名称/类型，后续实现不得增加冻结状态、额度维护、扣款配对或核销等逻辑。

## 8. 实现选型建议与待核对事项

以下为建议方案，正式编码前需核对项目现有模型、表结构和查询流程，若现有结构不支持则记录差异后再实现：

### 8.1 订单实体

- 当前代码中没有发现统一的订单实体；用户端 `/me/orders` 组合展示持仓和产品预约，后台用户表另有持仓记录和账单弹窗。
- 最小实现建议：新增预约资金订单专用模型，归属 `app/Modules/Balance`，并在用户订单页增加一个同模块数据查询结果。
- 不改造 `Position`、`ProductReservation` 来承载非持仓类余额变动，也不为此引入复杂的跨业务 `UNION` 查询。
- 在 `/me/orders` 增加独立的资金订单区块，按 `created_at`、`id` 倒序。统一时间线和跨类型分页留待有明确需求时再设计。

### 8.2 用户端兼容

- 管理员创建的订单默认为已完成/成功。
- 用户订单页显示名称、类型、金额和时间。
- 扣款金额以负号展示，解冻金额以正号展示；底层订单金额保存正数，方向由订单类型决定。
- 订单名称由管理员填写，按普通文本转义输出，不使用富文本渲染。

### 8.3 管理后台入口

- 推荐在用户管理列表或用户详情页增加 Filament 行操作 `[创建预约资金订单]`。
- 通过弹窗表单选择扣款/解冻、填写名称和正金额，并展示该用户当前余额供管理员参考。
- 从用户上下文发起可减少手工选择用户导致的误操作；余额展示仅供参考，最终计算以事务内锁定读取的余额为准。

### 8.4 账户流水与数据库字段

- 沿用现有账户流水模型记录管理员操作的完整金额，并关联新订单；扣款记录负的完整金额，解冻记录正的完整金额。余额字段按扣款下限规则更新，不要求流水金额等于余额字段的实际差值。
- 核对余额、订单金额和流水金额的数据库精度与范围，统一金额小数位限制。
- 核对订单名称字段长度；建议限制为不超过 255 个字符。
- 若新增或修改数据库结构，按项目规则同步更新迁移和 `database/sql/mvp_schema.sql`。

## 9. 逐项开发清单

以下路径依据当前仓库结构列出。带“新增”的路径是实施建议；若开发核对后发现已有等价实现，应复用现有实现并在提交说明中记载，避免重复造轮子。

### 阶段 A：数据结构

1. **新增迁移**：`database/migrations/<timestamp>_create_admin_reservation_fund_orders_table.php`
   - 字段建议：`id`、`user_id`、`type`、`name`、`amount`、`timestamps`。
   - `type` 区分扣款/解冻；`amount` 存管理员填写的正数完整金额；订单创建即完成，页面需要时直接显示“已完成”。订单发生时间使用 `created_at`，与流水的 `occurred_at` 取同一个操作时间。
   - `user_id` 外键关联 `users`，索引支持按用户筛选及按 `created_at`、`id` 倒序查询。
   - 不添加冻结金额、冻结状态、扣款关联/核销字段、操作管理员字段。
2. **同步 SQL 快照**：`database/sql/mvp_schema.sql`，同步新表定义、索引及外键。
3. **新增模型**：`app/Modules/Balance/Models/AdminReservationFundOrder.php`
   - 定义可写字段、金额/时间 casts、`user()` 关联。
4. **金额精度核对**：用户余额和 `BalanceLedger.amount` 当前按两位小数 cast；核对数据库列后沿用两位小数，不另造精度体系。

### 阶段 B：余额变更业务

5. **新增服务**：`app/Modules/Balance/Services/CreateAdminReservationFundOrderService.php`
   - 输入用户、类型、名称、金额。
   - 在 `DB::transaction()` 中对用户行使用 `lockForUpdate()`。
   - 扣款：订单/流水金额保留完整正金额，流水方向为负，余额按 `max(当前余额 - 金额, 0)` 更新。
   - 解冻：订单/流水金额保留完整正金额，流水方向为正，余额完整增加填写金额。
   - 创建订单及 `BalanceLedger`，将流水 `biz_ref_type`、`biz_ref_id` 指向订单；使用现有流水 `type` 约定前先检查所有当前枚举/字符串值及账单展示映射。
   - 不匹配扣款与解冻，不读取或维护冻结状态。
6. **余额运算约束**：使用数据库 decimal 字段及精确十进制/整数最小单位计算；不得用 PHP 浮点运算决定账变结果。复用现有余额服务的事务和用户行锁结构。金额计算始终使用定点数，并在事务内校验解冻后的余额能写入现有余额列。

### 阶段 C：管理后台

7. **修改用户列表操作**：`app/Filament/Resources/Users/Tables/UsersTable.php`
   - 增加 `[创建预约资金订单]` 行操作。
   - 表单项：操作类型、订单名称、金额；可显示当前余额作参考。
   - 操作调用创建服务，不在 Filament Action 闭包中直接拼装多表写入。
   - 金额必填且大于 0，按两位小数校验；名称必填且最大长度与数据库字段一致。
   - 提交过程中沿用 Filament Action 默认提交状态，降低重复点击概率。
8. **后台账单显示**：核查 `app/Filament/Resources/Users/Tables/UsersTable.php` 中现有账单弹窗及 `resources/views/filament/users/ledger-modal.blade.php`，确保新流水类型能显示名称、方向和完整金额；尽量复用现有账单视图。

### 阶段 D：用户端订单记录

9. **查询服务**：新增 `app/Modules/Balance/Services/ListUserAdminReservationFundOrdersService.php`，沿用现有订单列表服务的组织方式，按当前用户筛选，按 `created_at`、`id` 倒序返回展示字段。

## 10. 数据库与接口清单

### 数据库

- 新增 `admin_reservation_fund_orders` 表（表名可按项目实际命名约定调整）。
- 外键：`user_id -> users.id`；索引：至少支持按用户筛选及按 `created_at`、`id` 倒序读取。
- 不修改 `users.balance` 的负数规则；余额仍不低于 0。
- 复用 `balance_ledgers`，写入完整操作金额及现有 `before_balance`、`after_balance`。按已确认规则，流水完整金额不要求与余额字段差额相等。
- 同步 migration 与 `database/sql/mvp_schema.sql`。

### 应用接口

本功能使用 Filament 后台 Action 和现有 `/me/orders` 页面，不新增独立 HTTP JSON API。

- 写入入口：`UsersTable` 的行 Action -> `CreateAdminReservationFundOrderService`。
- 用户端读取入口：`PositionOrdersPageController` -> 资金订单查询服务 -> `orders.index` 视图。
- 输入字段：`type`（扣款/解冻）、`name`（管理员填写）、`amount`（正数，两位小数）。
- 服务输出：新建订单；后台显示成功通知，失败时事务回滚并按现有异常处理方式提示。
